a. 내가 읽은 기사 목록
b. 읽은 기사의 통계

#2. b가 쌓이면 그걸 바탕으로 추천까지 해줄 수 있다. 내가 좋아하는 영역, 잘 안 읽어본 영역 정도.

#3. 그리고 신문 읽기가 귀찮을 때가 있으므로 자동으로 요약시켜놓고 나중에 봐도 된다.

## 궁금한 점 -> 망한 점
나는 이걸 그냥 프로젝트용으로 써먹으려고 했다. 근데 이것도 해야지 저것도 해야지 하다가 뭔가 좀 버거워진 느낌이 들기 시작했다. 가장 큰 의문점은.. 사용자 관점에서 이 서비스의 의도를 어떻게 파악해야 할까?
A : 뉴스 기사 읽는 걸 좋아하는데, 제가 그동안 뭘 읽었는지 되돌아보고 싶어요.
B : 저는 뉴스를 볼 시간이 없네요 (또는 귀찮네요). 제가 '볼 거 같은, 봤으면 좋겠는' 뉴스 기사 요약만 해줬으면 좋겠어요.
C : 저는 뉴스 자주 봐요. 제가 읽을 뉴스를 추천해주세요.

A,B,C의 요구가 제각각이다. 나는 지금까지 이걸 모두 만족하는 서비스를 만들려고 했다. 스케일이 점점 커진다. '구현'의 함정에 빠져버렸다.

함정에 빠졌다는 사실을 전혀 모른 채 2주동안 미친듯이 개발을 했다. 그동안 쌓아온 기술 스택 다 갖다 붙이고, GPT 제미나이 형님들의 도움도 무지하게 받고, 혼자 하는거다 보니 htmx로 땜질하면서 프론트엔드 디자인도 힘들게 만들었다. 그렇게 지금까지 만든 결과는 A, B, C 모두의 요구를 만족한다. 오? 싶겠지만 개판이다. 

사용자가 유입되었을 때를 가정해보면 뉴스 요약 / 아카이빙 / 추천 모두 엉망진창이고, 사이트에 들어와서 얘가 나를 위해 뭘 제공하고 싶은건지 명확하지도 않고, 접근성도 떨어지고, 버그 투성이에 (오늘도 밤동안 내내 기사 안뜨는 문제를 고쳤다) 애초에 내가 원했던 '기술 스택 쌓고 포폴 알차게 채워서 눈에 띄기' 와 많이 멀어진 느낌이다.

그래서 약간의 갈아엎음이 필요할 것 같다. 한숨 돌리고(한숨 존나 쉬고) 계획부터 다시 짜보았다. 문어발 식의 기능들의 구현 순서를 정하고, 서비스의 목적을 명확하게 해야 했다.

## 갈아엎기

생각을 해보자.. 내가 끌고 싶은 어그로는 '크롬 확장프로그램을 통한 간편한 저장'이다. 기사 들어가서 확장프로그램 누르고 저장하고 보여주고. 딱 거기까지만 하자! 일단은. 뉴스를 통한 지식의 축적만 보여줘보자..

오케이. 가장 먼저 튀어오르는 문제는 이거다. 확장프로그램의 버튼을 눌렀을 때 '읽었는지 안읽었는지' 모른다는 거다. 읽고 버튼을 누른 거면 내 지식으로 들어가고, 안 읽고 버튼을 누른거면 '나중에 읽을 기사'가 된다. 읽지도 않은 기사를 아카이빙하는 것은 문제가 있을 것이다.

그러면 어떻게 해야 할까. 안 읽었어도 읽었게끔 만들면 된다. 궁여지책으로, AI 써준다. AI가 '누르면 일단 요약' 해주고, 그 요약을 읽는 것 만으로도 지식이 쌓였다고 쳐주는 거다. 읽든 안읽든 최소한 요약을 읽기까지 맥시멈 20초까지는 해당 기사에 머물 것이다. 그 다음 버튼 한 번 더 누르면 그게 내 지식이 되는 거다.





처음으로 기사 사이트에 들어와서 20초동안 사용자의 경험 플로우는 다음과 같다.

1 - 기사를 읽겠다는 기세로 들어온 경우 : 20초가 넘겠지만 상관없다. 다 읽고 버튼 눌러서 내 지식으로 아카이빙하면 된다.
2 - 애초에 안읽을 기세로 들어온 경우 : 들어오자마자 확장 프로그램 버튼을 누른다. 요약이 뜰거고, 잘 읽고, 이해하기까지 15~20초 걸린다. 마지막으로 버튼 누른다. 내 지식으로 '쳐 준다'.
3 - 읽다 말 경우 : 어쨌든 보긴 봤잖아. 20초 넘게 있었던게 어디야. 이것도 '쳐 준다'.

그럼 대충 읽은 기사를 왜 지식으로 쳐줘야 하는가? 현대인에게 필요한 능력은 모든 정보를 암기하는 것이 아니라, 어디에 무엇이 있는지 아는 능력이다. (아니어도 어쩔 수 없다 여기서부터는 우겨야 한다) 내 서비스는 100%의 깊이를 주는 것이 아니라, 100개의 정보에 접근할 수 있는 '지도'를 그려주는 도구다. 대충 읽었거나 안읽고 ai 세줄요약만 봤거나 어쨌든 봤으니까 머리속에 있을 거다. 근데 금방 까먹겠지. 난 그걸 안까먹게 통계로 주려고 하는거니까, 일단 지식으로 치고 통계에 포함시켜서 나중에 깊게 볼 수 있게끔 만들어주는 것이 좋을 것 같다.

한가지 경우가 남았는데, '요약 눌러놓고 그거조차 안 보고 그냥 도망간 쌥쌥이련' 이다. 이 경우 ai 요약 프로세스가 중단된 경우 DB state를 unread로 해놓고 따로 처리하거나 버리거나 하면 된다.



## 정리
아주 만족스러운 건 아닌데, 정리해보면 내가 할 일은 어느정도 가닥이 잡혔다.

* 강력한 크롬 익스텐션: AI 3줄 요약 결과가 스트리밍으로 최대한 빨리 팝업에 뜨게 구현 (입력 장벽 제거).
* UX Flow 설계: '읽음/안 읽음'의 모호함을 [Capture -> Confirm] 2단계 버튼으로 해결하여 데이터 정합성 확보.
* 지식의 시각화 (통계): "내가 이만큼 똑똑해졌다"는 것을 보여주는 Github 잔디 심기 스타일의 히트맵 구현.
* 검색(RAG) 구현: 저장된 지식이 죽은 데이터가 되지 않도록, Vector Search를 통해 "내 서재와 대화하기" 기능 탑재.
* 배포 및 데모: AWS에 배포하고, 면접관이 바로 눌러볼 수 있는 '데이터가 꽉 찬 데모 계정' 만들기.
